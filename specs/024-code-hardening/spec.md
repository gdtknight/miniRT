# Feature Specification: Code Hardening

**Feature Branch**: `024-code-hardening`
**Created**: 2026-01-31
**Status**: Draft
**Input**: Code review findings from docs/code-review-findings-024.md and docs/code-review-report.md

> **Scope Note**: docs/code-review-report.md의 "긴 라인 처리(1023바이트 제한)" 이슈(항목 1)는 023-parsing-robustness 기능에서 이미 해결됨 (4KB 버퍼, 4096자 라인 제한 구현). 본 스펙 범위에서 제외.

## Overview

코드 리뷰에서 식별된 9개의 결함을 수정하여 레이트레이서의 안정성, 정확성, 견고성을 향상시킵니다. 이슈는 렌더링 정확성(High), 특정 조건 오동작(Medium), 방어적 코딩(Low) 세 가지 범주로 분류됩니다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 정확한 BVH 기반 렌더링 (Priority: P1)

사용자가 다수의 오브젝트가 포함된 장면을 렌더링할 때, BVH 가속 구조가 활성화된 상태에서도 모든 오브젝트가 정확하게 표시되어야 합니다. 현재는 미초기화된 distance 값으로 인해 간헐적으로 오브젝트가 누락되거나 잘못 렌더링될 수 있습니다.

**Why this priority**: BVH는 기본 활성화되어 있으며, 모든 렌더링에 영향을 미치는 핵심 경로입니다. 미초기화 변수로 인한 비결정적 버그는 디버깅이 어렵고 사용자 경험을 심각하게 저하시킵니다.

**Independent Test**: 10개 이상의 오브젝트가 포함된 장면을 100회 연속 렌더링하여 모든 오브젝트가 일관되게 표시되는지 확인합니다.

**Acceptance Scenarios**:

1. **Given** BVH가 활성화된 상태에서 다수의 구/평면/실린더가 포함된 장면, **When** 렌더링을 실행하면, **Then** 모든 오브젝트가 정확한 위치와 색상으로 표시됩니다.
2. **Given** 동일한 장면과 카메라 설정, **When** 렌더링을 여러 번 반복하면, **Then** 매번 동일한 결과가 생성됩니다 (결정적 동작).

---

### User Story 2 - 축 정렬 뷰에서 정상 렌더링 (Priority: P1)

사용자가 카메라를 특정 축과 정렬된 방향(예: 정면, 측면 뷰)으로 설정했을 때, AABB 교차 테스트가 정상적으로 동작하여 장면이 올바르게 렌더링되어야 합니다. 현재는 ray 방향 성분이 0일 때 division by zero로 인해 렌더링이 깨질 수 있습니다.

**Why this priority**: 정면/측면/상단 뷰는 사용자가 장면을 검사할 때 자주 사용하는 기본적인 시점입니다. 이 시점에서 렌더링이 실패하면 프로그램 사용성이 심각하게 저하됩니다.

**Independent Test**: 카메라 방향을 (0,0,1), (1,0,0), (0,0,-1) 등 수평 축 정렬 방향으로 설정하고 렌더링이 정상 동작하는지 확인합니다. (수직 방향 (0,1,0)은 User Story 3에서 별도 테스트)

**Acceptance Scenarios**:

1. **Given** 카메라 방향이 (0, 0, 1)인 정면 뷰, **When** 렌더링을 실행하면, **Then** 장면이 정상적으로 표시됩니다 (NaN/INF 없음).
2. **Given** 카메라 방향이 (1, 0, 0)인 측면 뷰, **When** 렌더링을 실행하면, **Then** AABB 교차 테스트가 정상 동작합니다.

---

### User Story 3 - 위/아래 바라보기 정상 동작 (Priority: P2)

사용자가 카메라를 수직 위(0,1,0) 또는 아래(0,-1,0) 방향으로 설정했을 때, 화면이 정상적으로 렌더링되어야 합니다. 현재는 gimbal lock으로 인해 화면이 검정색으로 나오거나 깨집니다.

**Why this priority**: 위/아래 바라보기는 덜 빈번하지만 유효한 사용 사례입니다. 이 방향에서 완전히 실패하는 것은 사용자 경험을 저해합니다.

**Independent Test**: 카메라 방향을 (0,1,0)과 (0,-1,0)으로 설정한 장면 파일을 렌더링하여 정상 출력을 확인합니다.

**Acceptance Scenarios**:

1. **Given** 카메라 방향이 정확히 (0, 1, 0), **When** 렌더링을 실행하면, **Then** 위에서 내려다보는 뷰가 정상 표시됩니다.
2. **Given** 카메라 방향이 (0, 0.999, 0.001) 등 근사 수직, **When** 렌더링을 실행하면, **Then** 대체 up 벡터가 적용되어 정상 렌더링됩니다.

---

### User Story 4 - 다양한 윈도우 크기에서 타일 렌더링 정상 동작 (Priority: P2)

프로그레시브 렌더링이 실제 윈도우 크기에 관계없이 정확하게 동작해야 합니다. 현재는 800픽셀 하드코딩으로 인해 다른 크기에서 타일 계산이 잘못됩니다.

**Why this priority**: 윈도우 크기 변경은 일반적인 사용 패턴이며, 프로그레시브 렌더링은 UX의 핵심 기능입니다.

**Independent Test**: WINDOW_WIDTH를 1024, 640 등 다양한 값으로 설정하고 프로그레시브 렌더링이 전체 화면을 빠짐없이 커버하는지 확인합니다.

**Acceptance Scenarios**:

1. **Given** WINDOW_WIDTH=1024로 설정된 환경, **When** 프로그레시브 렌더링이 진행되면, **Then** 모든 타일이 올바른 위치에 렌더링됩니다.
2. **Given** 프로그레시브 렌더링 중, **When** 모든 타일이 완료되면, **Then** 화면에 미렌더링 영역이 없습니다.

---

### User Story 5 - 정확한 그림자 렌더링 (Priority: P2)

그림자가 표면의 실제 방향에 따라 올바르게 계산되어야 합니다. 현재는 고정 노멀 사용으로 인해 수직 벽면에서 shadow acne가 발생하거나 경사면에서 그림자가 떠 보입니다.

**Why this priority**: 그림자 품질은 시각적 사실감의 핵심 요소입니다. 잘못된 바이어스는 렌더링 결과의 품질을 저하시킵니다.

**Independent Test**: 수직 벽면(plane normal = (1,0,0))과 바닥면(plane normal = (0,1,0))이 포함된 장면에서 그림자가 표면에 밀착되어 렌더링되는지 확인합니다.

**Acceptance Scenarios**:

1. **Given** 수직 벽면 위의 그림자, **When** 렌더링을 실행하면, **Then** shadow acne 없이 부드러운 그림자가 표시됩니다.
2. **Given** 경사진 표면 위의 그림자, **When** 렌더링을 실행하면, **Then** 그림자가 표면에서 떠 보이지 않습니다 (peter-panning 없음).

---

### User Story 6 - I/O 오류 명확한 보고 (Priority: P3)

파일 읽기 중 디스크 오류나 권한 문제가 발생하면 사용자에게 명확한 오류 메시지가 표시되어야 합니다. 현재는 I/O 오류가 EOF와 구분되지 않아 조용히 실패할 수 있습니다.

**Why this priority**: I/O 오류는 드물지만, 발생 시 명확한 피드백이 없으면 사용자가 원인을 파악하기 어렵습니다.

**Independent Test**: line_reader의 io_error 플래그가 read() 실패 시 설정되고, 파싱이 오류로 종료되는지 코드 검사 및 단위 테스트로 확인합니다. (실제 I/O 오류 시뮬레이션은 /dev/full 또는 mock fd 사용)

**Acceptance Scenarios**:

1. **Given** read() 호출이 -1을 반환하는 상황, **When** line_reader_next()가 호출되면, **Then** io_error 플래그가 설정되고 NULL이 반환됩니다.
2. **Given** io_error가 설정된 상태, **When** 파싱 루프가 종료되면, **Then** 파싱이 성공으로 처리되지 않고 오류가 보고됩니다.

---

### User Story 7 - 비정상 입력에 대한 방어 (Priority: P3)

악의적이거나 잘못된 입력 파일에 대해 프로그램이 안전하게 오류를 처리해야 합니다. 정수 오버플로, 과도한 오브젝트 수, 범위 외 좌표 등에서 크래시 없이 오류를 보고해야 합니다.

**Why this priority**: 방어적 코딩은 프로그램의 견고성을 높이지만, 일반 사용에서는 드물게 트리거됩니다.

**Independent Test**: 매우 큰 정수 값(99999999999)이 포함된 .rt 파일을 파싱하여 오버플로 오류가 감지되는지 확인합니다.

**Acceptance Scenarios**:

1. **Given** 매우 큰 정수가 포함된 입력 파일, **When** 파싱을 시도하면, **Then** 오버플로 오류가 감지되고 적절한 메시지가 표시됩니다.
2. **Given** 범위 외 픽셀 좌표 접근 시도, **When** 렌더링 중 호출되면, **Then** 버퍼 오버런 없이 안전하게 무시되거나 오류가 보고됩니다.

---

### Edge Cases

- 카메라 방향이 정확히 (0, 1, 0) 또는 (0, -1, 0)일 때 어떻게 처리하는가?
- ray 방향의 모든 성분이 0에 가까울 때(영벡터) AABB 테스트가 어떻게 동작하는가?
- INT_MAX에 가까운 정수를 파싱할 때 오버플로가 정확히 감지되는가?
- object_list가 INT_MAX/2 이상의 capacity에 도달했을 때 어떻게 처리되는가?
- 픽셀 좌표가 정확히 경계값(width-1, height-1)일 때 정상 동작하는가?

## Requirements *(mandatory)*

### Functional Requirements

#### High Priority (렌더링 정확성)

- **FR-001**: BVH 리프 교차 검사에서 temp_hit.distance를 호출자가 전달한 hit->distance 값으로 초기화하여 상한 거리(clip distance)를 유지해야 합니다.
- **FR-002**: AABB 슬랩 테스트에서 ray 방향 성분이 0일 때 division by zero를 방지하고 올바른 교차 판정을 수행해야 합니다.

#### Medium Priority (특정 조건 오동작)

- **FR-003**: 카메라 방향이 world up 벡터 (0,1,0)과 평행할 때 대체 up 벡터를 사용하여 유효한 카메라 기저를 생성해야 합니다.
- **FR-004**: 프로그레시브 타일 계산에서 실제 윈도우 너비를 사용해야 합니다 (하드코딩된 800 제거).
- **FR-005**: 소프트 섀도우 바이어스 계산에서 실제 표면 노멀을 사용해야 합니다.
- **FR-006**: line_reader가 read() 오류(-1)와 EOF(0)를 구분하여 I/O 오류 발생 시 적절한 오류 상태를 설정해야 합니다.

#### Low Priority (방어적 코딩)

- **FR-007**: 정수 파싱에서 오버플로를 감지하고 파싱 오류로 처리해야 합니다.
- **FR-008**: object_list 확장 시 capacity * 2 오버플로를 검사하고 안전하게 실패해야 합니다.
- **FR-009**: 픽셀 읽기/쓰기 함수에서 좌표 범위를 검사하거나, 호출자 책임임을 명확히 문서화해야 합니다.

### Key Entities

- **t_hit_record**: 교차 검사 결과를 저장하는 구조체. distance 필드가 상한값으로 사용됨.
- **t_line_reader**: 버퍼링된 파일 읽기 구조체. io_error 필드 추가 필요.
- **t_progressive_state**: 프로그레시브 렌더링 상태. width/height 필드 추가 필요.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: BVH가 활성화된 상태에서 10개 이상의 오브젝트가 있는 장면을 100회 렌더링했을 때 100% 동일한 결과가 생성됩니다.
- **SC-002**: 카메라 방향이 축 정렬(예: 0,0,1)인 장면이 NaN/INF 없이 정상 렌더링됩니다.
- **SC-003**: 카메라 방향이 (0,1,0) 또는 (0,-1,0)인 장면이 검정 화면 없이 정상 렌더링됩니다.
- **SC-004**: WINDOW_WIDTH가 800이 아닌 값(예: 640, 1024)에서 프로그레시브 렌더링이 전체 화면을 빠짐없이 커버합니다.
- **SC-005**: 수직 벽면과 경사면에서 그림자가 표면에 밀착되어 렌더링됩니다 (시각적 검증).
- **SC-006**: I/O 오류 발생 시 프로그램이 해당 오류를 사용자에게 보고합니다.
- **SC-007**: INT_MAX를 초과하는 정수 입력 시 파싱이 오류로 처리됩니다.
- **SC-008**: 모든 수정 후 기존 테스트 장면(scenes/valid/*)이 정상 렌더링됩니다 (회귀 없음).

## Assumptions

- 픽셀 범위 검사(FR-009)는 함수 내 검사 추가 방식으로 구현합니다. 성능 영향은 미미할 것으로 예상됩니다.
- 카메라 up 벡터 대체 기준(dot > 0.999)은 대부분의 근사 수직 케이스를 커버합니다.
- 정수 오버플로 검사는 음수 오버플로도 포함합니다 (-INT_MAX 이하).
- object_list capacity 오버플로 검사는 실제로 트리거될 가능성이 매우 낮지만 방어적으로 추가합니다.

## Dependencies

- 023-parsing-robustness 기능이 병합된 상태여야 합니다 (t_line_reader 구조체 사용).
- 42 Norm v4.1 준수가 유지되어야 합니다.

## Out of Scope

- 새로운 기능 추가 없음 (기존 결함 수정만 해당).
- 성능 최적화 없음 (정확성 및 견고성 우선).
- 테스트 프레임워크 도입 없음 (수동 테스트로 검증).
- **긴 라인 처리 이슈** (docs/code-review-report.md 항목 1): 023-parsing-robustness에서 해결됨.
