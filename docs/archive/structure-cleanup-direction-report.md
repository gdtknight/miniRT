# 구조 정리 방향 리포트

작성일: 2026-02-08
범위: `src/`, `includes/` 구조 정리 방향 (현 코드베이스 기준)

---

## 1. 목표

- 모듈 경계 명확화
- 헤더/소스 간 의존성 최소화
- 유지보수 비용 감소
- 변경 범위를 단계적으로 축소

---

## 2. 기본 원칙

1. **기능 단위 디렉토리 유지**: `src/`의 현재 기능 분리는 유지한다.
2. **헤더 경계 강화**: public vs internal 헤더를 분리하여 의존성 확산을 억제한다.
3. **정책/행위 분리**: window는 이벤트 전달, render는 렌더 정책/로직 담당으로 역할을 분리한다.
4. **공용 유틸 최소화**: utils에는 범용 기능만 유지하고 모듈 전용 유틸은 해당 모듈로 이동한다.

---

## 3. 단계별 정리 방향

### Phase 1: 헤더 경계 정리 (우선순위 High)

**문제**: `includes/`가 flat 구조이며 internal 헤더가 노출됨

**방향**:
- `includes/internal/` 디렉토리 도입
- `window_internal.h` → `includes/internal/window_internal.h`
- 내부 전용 헤더는 접두사 `internal_` 또는 하위 폴더로 분리

**효과**:
- public API/내부 구현 경계가 명확해짐
- 외부 모듈의 잘못된 include 방지

---

### Phase 2: render vs window 역할 경계 정리 (우선순위 Medium)

**문제**: window가 렌더 정책에 깊게 관여함

**방향**:
- render 정책 로직을 `render/`로 이동
- window는 입력/이벤트 전달 및 MLX 래핑 역할에 집중

**구체 방향**:
- `window_loop.c`: 렌더 루프 정책 → `render/`로 이동 검토
- `render_flags_set.c`: render 정책 성격이 강하므로 `render/` 이동 고려

**효과**:
- 렌더 정책과 플랫폼 의존 로직 분리
- 테스트/리팩터링 난이도 감소

---

### Phase 3: utils 재분류 (우선순위 Low)

**문제**: utils 범위가 광범위하고 모듈 전용 기능이 섞임

**방향**:
- parser 전용 유틸 → `parser/` 하위로 이동
- 렌더 전용 유틸 → `render/` 하위로 이동
- 공용 유틸만 `utils/` 유지

**효과**:
- 모듈 독립성 강화
- 필요 없는 간접 의존 제거

---

## 4. 리스크 및 대응

| 리스크 | 영향 | 대응 |
|-------|------|------|
| 헤더 경로 변경 | include 오류 | 단계별 적용 + include 경로 일괄 수정 |
| 모듈 이동 | 빌드 깨짐 | 작은 단위로 이동, 변경 범위 최소화 |
| 역할 경계 재정의 | 구조 혼란 | 역할 정의 문서화 및 작업 순서 고정 |

---

## 5. 우선순위 요약

1. **Phase 1**: internal 헤더 분리
2. **Phase 2**: window/render 역할 경계 정리
3. **Phase 3**: utils 재분류

---

## 6. 결론

구조 정리의 핵심은 “헤더 경계 강화”와 “window/render 역할 분리”이다. 전면적인 디렉토리 변경보다, 내부 헤더 분리와 정책 위치 조정처럼 **작고 명확한 구조 개선**부터 진행하는 것이 리스크 대비 효과가 가장 크다.
